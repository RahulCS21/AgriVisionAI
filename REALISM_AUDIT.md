# AgriVision AI Realism and Data Audit

## Summary

The application no longer presents synthetic yield estimates or invented weather values as real observations. Its live weather screen queries Open-Meteo for locations in India and shows no weather metrics unless a live lookup succeeds. Crop screening and soil guidance remain transparent rules-based decision-support tools, not validated AI predictions.

## What is real and operational

- **Weather:** The application queries the Open-Meteo Geocoding API and Forecast API. Location results are restricted to `IN`; forecasts provide temperature, relative humidity, hourly precipitation probability, and wind speed. Network requests have a timeout, provider errors are reported without demo-value fallbacks, and forecast data is labeled model-based.
- **Prediction history:** New successful crop-screening and fertilizer-guidance submissions are stored in SQLite. A disease result is stored only when inference returns a result from a configured model.
- **Upload handling:** Disease image uploads are limited by the request-size cap and checked against supported filename extensions and file signatures. Filenames are generated by the server; admin deletion uses a constrained upload path.
- **Language selector:** The interface supports English, Hindi, Kannada, Tamil, and Telugu. Model labels and crop names remain as supplied when translated equivalents are not available.

## What is rules-based or educational

- **Crop Recommendation:** A manually curated screening compares Rice, Wheat, Maize, Cotton, Sugarcane, Millets, and Pulses against broad soil, Kharif/Rabi/Zaid, temperature, and seasonal-rainfall bands. The factor-level reasoning is displayed. The rules are not an AI model, are not district-specific, and are not an official crop calendar or crop plan.
- **Fertilizer Recommendation:** The form records N, P, and K lab values and uses the farmer-selected Low/Medium/High Soil Health Card ratings for qualitative guidance. Numeric values do not determine advice or fertilizer dosage. No application rates are calculated. Guidance references common fertilizer sources and directs farmers to crop- and district-specific Soil Health Card or state recommendations and a local KVK.
- **Disease guidance:** The disease guidance catalogue is static educational material mapped to PlantVillage class names. It is not evidence that a disease has been detected, and it is not a regionally validated treatment prescription. The interface advises farmers to seek local agricultural guidance.

## What is unavailable

- **Crop Yield Prediction:** The recovered Local History CSV contains 10 generic records with temperature, rainfall, humidity, and yield, but no source, units, crop, district, season, or year. A demonstration-only LinearRegression model is trained from that snapshot and the app labels every output “Demonstration Prediction,” discloses that it is not production-grade, notes the undocumented target units, and stores successful results. The model has not been independently evaluated and must not be used for real agricultural planning.
- **Disease Detection:** No trained disease model is bundled. Without a compatible trained model and its runtime dependency, uploads are not classified and no disease name, confidence, or prediction-history entry is created. The existing screen presents this limitation instead of a fabricated result.

## Data sources

| Data | Source | Use and limitations |
|---|---|---|
| Indian location lookup | [Open-Meteo Geocoding API](https://geocoding-api.open-meteo.com/v1/search) | Public location search constrained to India; requires internet access. |
| Current conditions and precipitation probability | [Open-Meteo Forecast API](https://api.open-meteo.com/v1/forecast) | Forecast/model-derived conditions, not guaranteed local station observations; requires internet access. |
| Crop suitability bands | Application-maintained rules in `agriculture.py` | Broad screening only; not sourced from a live or official district-level agronomy dataset. |
| Fertilizer recommendations | Application-maintained qualitative guidance using user-entered Soil Health Card ratings | Does not calculate doses or replace the farmer's crop-specific Soil Health Card. |
| Disease advisory text | Application-maintained educational catalogue in `disease_guidance.py` | Not a diagnostic model or a verified local treatment database. |
| Historical activity | Local SQLite database | Existing rows were preserved. Rows from earlier versions may have been produced by unvalidated logic and cannot be independently verified. |

No ICAR, state agriculture university, IMD, district crop-calendar, or validated yield-training dataset is currently integrated.

## Security and operating notes

- Public form submissions use CSRF tokens. Uploads are constrained by a 5 MB request limit, extension/signature validation, and server-generated filenames.
- The default session secret is process-local if `AGRIVISION_SECRET_KEY` is unset. Configure a persistent secret before deployment; otherwise sessions will not survive process restarts.
- Weather access requires outbound internet. The application does not fabricate a fallback when the provider is unavailable.
- Existing prediction-history records and uploaded images were not purged. The history and report screens warn that legacy model provenance and results have not been independently verified.

## Recommended remaining work

1. Obtain licensed, traceable Indian yield data with crop, district, season, year, and management context. Document provenance, missingness, and representativeness.
2. Obtain traceable yield data and evaluate production yield models with time- and location-aware holdouts, publish metrics and supported ranges, and validate them with agronomists before presenting any output as production-grade.
3. Source and validate an India-relevant plant-disease model and treatment references. Verify class mapping, calibration, out-of-distribution handling, and local expert review before displaying diagnoses.
4. Replace broad crop screening bands with reviewed state/district crop calendars, rainfall normals, irrigation context, soil-test interpretation, and variety-specific guidance.
5. Validate fertilizer guidance against official crop- and district-specific recommendations and explain how Soil Health Card categories and units are interpreted.
6. Add weather caching, rate limiting, service monitoring, and clear provider attribution appropriate for deployment.
7. Add provenance/version fields to prediction-history records and a migration or explicit legacy marker so older records can be distinguished from future validated outputs.

## Verification performed

The Python modules compile, and the project test suite passes (41 tests). Weather tests mock provider responses and verify the India restriction, successful metric parsing, and failure handling. The test suite does not make an external weather request; live provider availability was not verified as part of these tests.
